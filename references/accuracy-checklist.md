# Accuracy checklist (run before sending each module)

The learner usually can't tell when a lesson is wrong. Self-study has no TA to catch mistakes, so check the module as a careful TA would before it goes out.

## Numbers and code
- Recompute every number, estimate, and worked answer. Show the arithmetic for estimates, e.g. "10¹² ÷ 10⁷ ops/s = 10⁵ s ≈ 1 day".
- State the assumption behind each estimate and the conditions behind each claim (worst or average case, short or long run, which version).
- If you can run code, run the snippets, exercises, and mini-projects, and describe the output you actually got. Check every "you should see X" against the lesson's own code.
- When a number appears more than once, derive each mention from the same source. Check that units and labels in tables match the definitions in the text. When the text names a maximum, minimum, or turning point, make sure the table or example actually shows it.

## Evidence and claims
- For each named study, give researchers and year correctly. If the run date and publication date differ, say so. If you're unsure of a detail (sample, materials, exact percentages), describe the study only at the level you're sure of.
- Note replication status where it's known, and mark contested theories as contested. Say "offered an influential explanation", not "proved" or "resolved".
- Flag behavior that depends on a tool, version, or implementation instead of presenting it as universal.
- If a web search tool is available, use it to check the reading's table of contents, direct quotes, and anything time-sensitive (current events as of today's date). Don't hand the check back to the learner when you can do it.

## Concepts and examples
- Make each example fit the concept's definition exactly, not a neighboring concept (e.g. diffusion of responsibility isn't social loafing).
- When you name a domain tool or method (a clinical protocol, a framework, a library), state its designed purpose in a few words. If the way you're using it doesn't match that purpose, drop it.
- Make scenarios realistic for the learner's field. A professional will spot one that breaks their real-world norms.
- Check that each analogy doesn't distort the formal definition, and say where it breaks down.
- When a textbook is assigned, match its notation and the form of its definitions (in your own words), so the learner isn't confused when they read it.

## Coverage and fit
- Go through the assigned reading's section list, not just the syllabus topic line. Cover each section or explicitly defer it to a later module.
- Define every term before an exercise or quiz relies on it.
- Teach background the exercises rely on (e.g. log identities), and cite where it lives: the exact chapter or appendix, not the week's reading range.
- Tag every practice and quiz item with the objective it serves (e.g. `[O2]`). Each objective needs at least one item that uses its exact verb and count ("calculate" means a numeric problem, "name two" means asking for two). Don't set practice that the lesson already answered word for word, and make counts in instructions match the lesson ("list six events" needs six).
- Size the module to the weekly budget. Add up every timed activity, including assigned reading (or say explicitly that the reading is optional). Required work fits the hours, and anything beyond that is labeled optional. Cut repetition before cutting substance.
- Keep self-audit notes short. The learner needs one line saying what's covered and what's deferred, not your full checklist.

## Citations, answer keys, and summaries
- Give a chapter's or section's exact title only after verifying it against a published table of contents or the learner's copy. Otherwise give the number and topic and say the title is unchecked. A confident wrong title is worse than none.
- Quote exact wording only when you've checked it against the primary source. Otherwise paraphrase.
- Describe sources accurately (a community wiki isn't an "official reference").
- Check every answer-key label against the lesson's own definitions and lists. Each justification must actually imply its conclusion, not just reach the right answer.
- Answer keys should accept other defensible answers and say why they're also reasonable.
- Summary and closing lines must not claim more than the caveats allow (e.g. don't say "covers PS2" when PS2's content is unknown, or "all of Ch. 5" unless you checked its table of contents).
